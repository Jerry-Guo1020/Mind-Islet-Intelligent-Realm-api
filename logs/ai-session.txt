[2026-10-21] 信箱图谱补数：count / weight / totals + 全量来信接口
============================================================
做了什么
- 按 docs/superpowers/plans/2026-10-21-mailbox-graph-api.md（在前端仓 healthy-island_副本/docs/superpowers/plans/）实现，同步设计出处是该前端仓的 specs/2026-10-21-mailbox-atlas-redesign-design.md §2.4。
- GET /api/mailbox/graph 现在返回 nodes[].count（这个关键词下有几封信）、edges[].weight（两个关键词共现几封信）、totals{letters, keywords}。
  实现上从「一次 findMany + 一个 seen 集合」改成「findMany + count 并发（Promise.all）+ 两个 Map」，计数在 Map 上顺手累加；
  nodes 的插入顺序仍按 createdAt asc 首次出现，前端不用排序。
- totals.letters 必须单独 count() 一次，理由两条：一封信可以带好几个关键词，所以 Σnode.count 会大于信数；
  而 records.length 只是「抽出了关键词的信」。标题组要写「N 封信」、且要和「全部来信」列表长度一致，所以按 where 数全部记录（这里刻意不叫 Σcount）。
- 顺手修掉一个潜伏 bug：同一封信里若有关键词 id 重复（关联表理论上不会，但 sort() 之后重复 id 相邻），两两配对会造出一条 n1→n1 的自环（图上是一条长度 0 的线）。改成先 Map 去重再排序，并有专门用例钉住。
- 新增 GET /api/mailbox/letters?year=&month=&mood=，一次取回全部来信（不按关键词筛，但年/月/情绪照筛）。
  路由声明在 @Get('letters/:recordId') **之前**：静态路径写在带参数的前面是 Nest/Express 里更稳的写法，否则 'letters' 会被当成 recordId。
  用反射读装饰器确认了注册顺序：graph → letters → nodes/:id/letters → letters/:recordId。
- letters() 与 allLetters() 抽成共用的私有 list(userId, query, extra)，两者唯一的分歧就是 extra（一个带 nodes:{some:{id}}，一个空），
  这样字段与排序永远不可能漂；有一条用例直接比对两条路由返回的键集合与整对象相等。
- 前端动机（写在 allLetters() 的注释里）：前端原来自己拉图、再按每个关键词并发打 N 次 nodes/:id/letters、再在本地合并去重（utils/mailbox-flow.js 的 mergeMailboxLetters），
  20 个关键词就是 20 次往返，还依赖「每封信都至少有一个关键词」这个不成立的假设。
